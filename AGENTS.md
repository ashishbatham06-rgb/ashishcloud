# Ashish Cloud — project rules

- Clients never write to the database directly; all INSERT/UPDATE/DELETE on `public` app tables goes through server functions using `supabaseAdmin` (service_role). Direct Data API write privileges are revoked from `anon`/`authenticated` (`files`, `folders`, `share_links`, `trusted_devices`, `profiles`), so if new code tries a client-side write it will fail — route it through a server function instead. Why: a malicious logged-in user with their own JWT could otherwise escalate quota, un-disable their account, or hijack file rows (e.g. point `r2_key` at another user's object) straight through the REST API.
- `profiles` allows only column-level `UPDATE (display_name, avatar_url)` for `authenticated`; privileged columns (`storage_quota_bytes`, `storage_used_bytes`, `disabled`, `email`, `phone`, `id`) are enforced by trigger `profiles_privileged_cols_guard` (service_role/postgres only) plus column grants. Keep both layers when changing profile update logic.
